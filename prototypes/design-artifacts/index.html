design:product

Reactor-control behavior contract

synthesized from resolved Decision Tickets · no re-interview

Problem statement

The STM32F103 is end-of-life. The product must keep running with no change in what operators, the SCADA host, and commissioning engineers observe, because re-qualification of every deployed site is economically unacceptable.

Success and measures

  • Behavioral equivalence: 100% of field functional test vectors pass on new hardware with identical pass criteria (the exit evidence gate).
  • Real-time budgets: worst-case control-loop response and comm latency unchanged within measured budget.
  • Wire compatibility: Modbus frames and HMI protocol byte-identical.
  • No site re-qualification; single factory re-qualification before field cutover.

Actors and flows

  • Operator — HMI: setpoint entry, mode change, fault acknowledge.
  • SCADA host — Modbus RTU: poll inputs, write setpoints/modes.
  • Commissioning engineer — serial diagnostic tool: calibration, loop tuning.
  • Watchdog — safe-state supervisor on firmware stall.

Behavioral contract

  • States: BOOT → SELF-TEST → RUN, with FAULT and SAFE states reachable from RUN.
  • Interactions: every write is validated and clamped before application; comms loss > 5 s forces a controlled safe state.
  • Rules: setpoints clamped to rated range, ramp-rate limited, faults latch until acknowledged.
  • Edge behavior: brownout during config write leaves last-good config intact; watchdog timeout always lands in SAFE.

Out of scope

  • No new features, no protocol changes, no HMI redesign, no new diagnostics.

Alternatives traceability

  • Platform choice (STM32H743) — decided by Decision Ticket "Select replacement processor platform".
  • Behavior-preservation (vs feature refresh) — decided by Decision Ticket "Adopt a behavior-equivalence exit gate".
  • Single factory re-qualification — decided by Decision Ticket "Re-qualification strategy".

Linked decisions & Evidence index

  • Decision Map #1 → Decision Tickets (3, linked above) → Evidence (processor benchmarks, field test vector library, EOL notice).
  • Domain Documentation: CONTEXT.md (Product Design, Transition Design terms).

design:technical

H743 migration — System / Program / Transition

synthesized from settled decisions · approval implicit (next step = Delivery Tickets)

System Design cross-component, language-neutral

Context & boundaries — Same board role, new MCU. External interfaces unchanged: sensors (ADC/SPI), actuators (PWM/GPIO), SCADA (UART/Modbus RTU), HMI (UART), watchdog (independent IWDG).

Components, responsibilities, dependency direction — Application layer (control loops, state machine) → Service layer (comm, HMI, watchdog) → HAL/BSP → MCU registers. Dependency strictly downward; application code never touches registers directly.

Semantic & temporal contracts — Frame formats unchanged; control loop 1 ms, comm 10 ms, jitter ≤ 20 µs, fixed interrupt priority map.

Quality-attribute scenarios — Worst-case ISR latency under D-cache miss; Modbus poll storm; brownout mid-config-write; watchdog fault injection.

Constraints & unknowns — New-part availability, H7 silicon errata, cache/MPU behavior, compiler-version differences in generated code.

Alternatives & tradeoffs — HAL vs register-level (HAL, for portability); bare-metal vs RTOS (bare-metal now, RTOS evaluated later); DMA vs bit-banged comm (DMA).

Current → target delta (stated once; Transition owns traversing it):

Current (F103)Target (H743)
CPUCortex-M3 @ 72 MHzCortex-M7 @ 480 MHz
Flash / SRAM64 KB / 20 KB1 MB / 512 KB
PeripheralsF1 mappingH7 mapping (remapped pins, new timer/ADC cores)
Bootsingle-bank flashdual-bank flash, vector relocation
ToolchainIAR EWARMGCC ARM (pinned, reproducible)

Program Design in-code shape · Embedded

  • Module/type layout — Same module graph: app_control, app_state, hal_*, bsp_*, comm_modbus; explicit types for states/setpoints.
  • Call trees — control loop: tick → app_control_step → HAL reads → PID → actuate; comm receive: ISR → ring buffer → comm_modbus.
  • Dependency direction within components — HAL above BSP, BSP above registers; no reverse links.
  • Testing seams & strategy — HAL seam enables host-side tests; target-in-the-loop harness runs on both old and new hardware.
  • Patterns / depth check — hardware access through BSP only; state-machine pattern; SOLID/CUPID suggested (not enforced); testable-design depth check passes.

Transition Design present — behavior is preserved

  • Baseline behavior-and-resources evidence — Field test suite pass record, timing/utilization measurements, vector/register tables, toolchain provenance captured before first slice.
  • Transition slices — 1) boot + clock + LED; 2) ADC/PWM control loop; 3) comms (Modbus/HMI); 4) watchdog + safe-state; 5) full-system equivalence run on the HIL rig.
  • Platform seams — HAL/BSP isolates the app from the MCU; old and new boards run in parallel rigs sharing one test harness.
  • Coexistence & compatibility — Separate firmware images per board, wire-identical outputs, one shared test oracle.
  • Rollback & irreversible — Full reflash to old board possible until factory cutover; irreversible step is field deployment.
  • Entry / exit evidence gates — entry: baseline suite green on old HW; per-slice: its vectors green on new HW; exit: full suite green on new HW at identical criteria + timing budgets met.

Embedded profile lens additive concerns

  • Boot/vector/linker/ABI/runtime/memory — dual-bank boot, vector relocation, linker-map delta, FPU/ABI choice (use soft-float to keep byte-identical math), startup/runtime init.
  • HAL/BSP/driver boundaries — unchanged seam, remapped driver implementations only.
  • ISR/task/DMA shared-state matrix — every shared buffer + which ISR/task touches it; volatile/atomic access rules.
  • Timing/utilization & memory budgets — worst-case ISR latency, CPU %, stack usage per task/ISR.
  • Cache/MPU/DMA/endian/alignment — D-cache + DMA coherence, MPU regions, alignment of packed structures.
  • Watchdog & safe-state — independent watchdog, safe-state ladder.
  • Vendor/generated provenance — CubeMX output isolated in vendor/, regeneration diffs recorded.
  • Reproducible toolchain evidence — pinned GCC, build checksums.
  • Verification strategy — host/simulator/target/HIL; old board = behavioral-equivalence oracle, new board = candidate; staged bring-up diagnostics + cutover evidence.

What We're Not Doing

  • No RTOS adoption in this effort (evaluated as a future decision). No new comm protocol. No per-site field re-qualification.

design:technical

hydrant release pipeline — System / Program / Transition

Medium materialization · Python profile

System Design cross-component, language-neutral

Context & boundaries — Repo, CI (GitHub Actions), PyPI, contributor environments. Build backend switches setuptools → hatchling; versioning via hatch-vcs.

Components, responsibilities, dependency direction — CI pipeline (build → test → publish) → release wrapper CLI → packaging config → PyPI. Repo config owns metadata; no runtime code owns release logic.

Semantic & temporal contracts — Semver from git tags; artifact names stable (hydrant-<ver>.tar.gz/.whl); publish runs only after test + lint gates pass.

Quality-attribute scenarios — Release attempted from a dirty tree; publish partially fails and retries; contributor without local tags still builds from checkout.

Constraints & unknowns — PyPI token handling (CI secret only); Python 3.9–3.12 support matrix; existing CI jobs must keep passing during the switch.

Alternatives & tradeoffs — hatchling vs poetry vs pdm (hatchling: lightweight, single-purpose); hatch-vcs vs setuptools-scm; CI-only vs local wrapper (wrapper kept for parity).

Current → target delta (stated once):

CurrentTarget
Build backendsetuptools (setup.py)hatchling (pyproject.toml)
Version sourcemanual bumphatch-vcs from git tags
Publishhand-runCI-gated + TestPyPI dry-run
Local devpip install -epip install -e (unchanged)

Program Design in-code shape · Python

  • Module/package layout — Public hydrant API surface unchanged; packaging metadata fully declared in pyproject.toml; optional hydrant.release internal module for the wrapper.
  • Call trees / import direction — release → hatchling build → CI publish step; tests import the public API only; no circular imports.
  • Typing strategy — py.typed marker, mypy strict on new code.
  • Lint/format/test-harness — ruff + black, pytest layout unchanged.
  • Async/concurrency — CLI is synchronous; note the blocking boundary, no async needed.
  • Testing seams/strategy — TestPyPI dry-run in CI; local pip install -e as the dev loop.

Transition Design thin — replaces existing build/release behavior

  • Baseline evidence — current manual release steps documented; current CI job outputs captured.
  • Slices — 1) pyproject conversion with no behavior change; 2) CI builds + tests on hatchling; 3) TestPyPI dry-run publishes; 4) cut over live publish + tagging.
  • Coexistence — keep a setup.py shim until slice 4 so existing contributor docs still work.
  • Rollback & irreversible — revert to setuptools config before slice 4; irreversible = first PyPI release from the new backend (a published distribution).
  • Gates — entry: existing CI green; exit: TestPyPI artifact installs in a fresh venv with matching checksums.

Python profile lens additive concerns

  • Packaging/deps — hatchling, dependency groups, requires-python ≥ 3.9.
  • Interpreter/venv/toolchain — support 3.9–3.12; dev via uv/pip.
  • Public API shape — CLI unchanged; new hydrant.release stays internal.
  • Performance/IO/memory — negligible; noted, no profiling needed.

What We're Not Doing

  • No repo-wide switch to another build tool, no Rust extensions, no releasing dev tooling as a package.

Representative project: adding a session export action to the settings page of a web app. Small, single-surface change — the whole design lives on the Effort root and its one Delivery Ticket.
Effort

Session export on Settings

role: Effort (root) · Small — no separate design records

Product intent

  • Problem — users cannot download their own session data.
  • Success — a Settings button downloads all visible sessions as sessions.json; 10k sessions export in < 2 s.
  • Behavior — clicking Export starts a download of everything the user can see; the UI stays responsive.

Concise System + Program design on the root · TS/Web at shallow depth

  • System — Settings page → API client (getSessionsExport) → GET /api/sessions/export → storage query. One new route, dependency direction unchanged.
  • Program — one component handler on the Settings page, one API-client method, one server route, one service function that builds export rows (the test seam).
  • Type strategy — reuse existing DTO types; no strictness change.
  • Client/server flow — fetch → blob → download; one awaited call, non-blocking.
  • Build/bundler — no config change; no new dependencies.
  • Testing — unit-test the service function + one e2e happy path.

Out of scope / not doing

  • CSV export, exporting other data types, streaming, pagination improvements.

Delivery

  • One self-contained Delivery Ticket (tracer bullet) carrying this design; implementation fits a single fresh context window.
The Delivery Ticket condenses this intent; no Design Artifact records are materialized for a Small effort.
