design:product

Reactor-control behavior contract

per create-prd template · synthesized from resolved decisions, no re-interview
Problem to Solve

The STM32F103 is end-of-life. The product must keep running with no change in what operators, the SCADA host, and commissioning engineers observe, because re-qualifying every deployed site is economically unacceptable.

What success looks like, and how we measure it
  • Behavioral equivalence — 100% of field functional test vectors pass on new hardware with identical pass criteria (the migration exit gate).
  • Real-time budgets — worst-case control-loop response and comm latency unchanged within measured budget.
  • Wire compatibility — Modbus frames and HMI protocol byte-identical.
  • No site re-qualification — single factory re-qualification before field cutover.
Proposed Solution
  • Keep the same product: same HMI, same SCADA contract, same control behavior.
  • Swap the platform under it — app code unchanged, BSP/HAL rewritten.
  • Prove equivalence on a hardware-in-the-loop rig where the old board is the oracle.
Alternative solutions considered
  • Feature refresh alongside the migration — rejected: triples re-qualification surface.
  • Per-site re-qualification — rejected: economically unacceptable.
Out of Scope
  • No new features, no protocol changes, no HMI redesign, no new diagnostics.
design:technical

H743 migration — Technical Design Document

per create-tdd template · System Design then Program Design · approval implicit by starting the next step
System Design

Cross-component architecture: how the pieces fit together, and how that arrangement changes from today. The delta is one coherent story — a platform swap, not a rewrite.

The app's component graph carries over unchanged; only the platform layer is rewritten

Application logic, services, and their dependency direction are today's design and stay today's design. What changes sits entirely below the HAL seam.

flowchart TD
    APP["App layer<br/>control loops · state machine<br/>UNCHANGED"] --> SRV["Service layer<br/>comm_modbus · hmi · watchdog<br/>UNCHANGED"]
    SRV --> HAL["HAL seam<br/>driver interfaces<br/>REWRITTEN for H7"]
    HAL --> BSP["BSP<br/>clock · mem · pins<br/>NEW for H7"]
    BSP --> MCU["STM32H743"]
    MCU --> SENS["sensors · actuators · UARTs"]

Every wire interface stays byte-identical, so SCADA, HMI and sensors cannot tell the boards apart

The external contracts are frozen — they are the equivalence target. Represented as wire shapes, not prose:

Modbus RTU frame (unchanged)
  addr: u8 · function: u8 · data: n×u8 · crc16: u16
  functions: 03 read regs · 06 write reg · 16 write multi
  registers: 0x0000..0x01FF (inputs) · 0x1000..0x10FF (setpoints)

HMI packet (unchanged)
  { STX, cmd: u8, len: u8, payload[len], crc8 }

Sensor reads (unchanged)
  read_sensor(ch) -> u16   @ 1 kHz, SPI + GPIO chip-select

The delta is one platform swap — new MCU, remapped peripherals, new toolchain

Current — STM32F103
CPU        Cortex-M3 @ 72 MHz
Flash      64 KB (single-bank)
SRAM       20 KB
Clock      HSE 8 MHz → PLL
Periphs    F1 ADC/timer/UART map
Boot       single-bank flash
Toolchain  IAR EWARM
Packaging  compiler-version-dependent
Target — STM32H743
CPU        Cortex-M7 @ 480 MHz
Flash      1 MB (dual-bank)
SRAM       512 KB (plus cache)
Clock      HSE 8 MHz → PLL → 480 MHz
Periphs    H7 ADC/timer/UART map
Boot       dual-bank, vector relocation
Toolchain  GCC ARM (pinned, reproducible)
Packaging  build checksums in CI

Quality attributes that must survive the swap — the numbers are part of the contract:

1 kHz ± 20µscontrol-loop cadence
≤ 15µsworst-case ISR latency incl. cache miss
80%stack headroom per task/ISR
0tolerated divergence vs oracle

Real-time and fault contracts are the equivalence oracle, not the goal

The only new software risk is silent behavioral divergence. The HIL rig makes divergence visible on every test vector — old board as oracle, new board as candidate, zero tolerance.

sequenceDiagram
    participant H as Test harness
    participant O as Old board (F103 · oracle)
    participant N as New board (H743)
    participant E as Comparator
    H->>O: same test vector
    H->>N: same test vector
    O-->>E: expected outputs (timing + values)
    N-->>E: actual outputs
    E->>E: diff — tolerance: none
    E-->>H: pass / fail

Shared state crosses ISR/task/DMA boundaries through a governed matrix

The new cache/DMA topology is where the classic "works on the bench" races hide. Every shared buffer is declared in one matrix with its accessors — this is the cross-component data contract for concurrency:

Program Design

In-code shape of the change. App modules are untouched; the views below show what is new or modified below the HAL seam and how it stays testable.

The 1 kHz control path is a straight call tree with no blocking calls

SysTick_Handler                       @ 1 kHz
  app_control_step(ctx)
    sensor_batch_read()               hal_sensor
      bsp_spi_transfer(...)           bsp
    pid_step(ctx->loop)               pure · host-testable
    actuate(ctx->output)
      bsp_pwm_set(ch, duty)           bsp
    comm_modbus_poll(ctx)             service · non-blocking

The file delta is a swap below the HAL seam; app/ and vendor/ are untouched

 app/control/app_control.c          # UNCHANGED
 app/state/app_state.c              # UNCHANGED
 hal/
 +  hal_sensor_h7.c                 # NEW — H7 ADC core mapping
 +  hal_actuator_h7.c               # NEW — new timer/PWM channel map
 ~  hal_comms_h7.c                  # MODIFIED — DMA + D-cache flush
 bsp/
 +  bsp_clock_h7.c                  # NEW — 480 MHz, dual-bank boot
 +  bsp_mem_h7.c                    # NEW — MPU regions + cache policy
 -  bsp_clock_f1.c                  # REMOVED
 vendor/
   stm32h7xx_hal_driver/            # vendor · provenance tracked

The HAL seam is the dependency-injection map: host tests fake it, HIL keeps it real

app_control_step
  receives ctx->sensors (hal_sensor)   -> host tests fake a sensor batch
  receives ctx->loop                   -> pure PID, host-testable
  receives ctx->comm                   -> comms faked in loop tests

hal_sensor
  receives bsp_spi_transfer            -> hardware boundary, target-in-loop only

Key signatures — the new BSP/HAL surface is small and typed

void      app_control_step(ControlCtx *ctx);          // 1 kHz, no blocking calls
uint16_t  bsp_adc_read(adc_ch_t ch);                  // ~2.5 µs, 12-bit
void      bsp_pwm_set(pwm_ch_t ch, uint16_t duty);    // 20 kHz output
void      bsp_mem_flush_dcache(void *buf, size_t n);  // before DMA ownership handoff

Fault handling is a table-driven state machine, not if/else sprawl

on(1 ms tick)
  if state == FAULT and ack asserted
    state = SAFE
  if state == RUN
    read sensors → pid → clamp → actuate
    if any fault bit
      state = FAULT
      latch cause into fault_register
What We're Not Doing
  • No RTOS adoption in this effort (evaluated as a future decision).
  • No new comm protocol, no HMI redesign, no feature refresh.
  • No per-site field re-qualification.

Automate hydrant packaging & releases

per create-prd shape, kept on the root (tooling — not interaction-rich)
Problem to Solve

Releases are manual and brittle: metadata lives in setup.py, publish is hand-run, and there is no locked CI gate.

Success & measurement

Out of Scope

hydrant release pipeline — Technical Design Document

per create-tdd template · Medium materialization · Python profile
System Design

CI is the only publisher; the local release command delegates to the same gates

flowchart LR
    DEV["Contributor"] --> REL["hydrant release"]
    REL --> GATE{"gates<br/>lint + test + clean tree"}
    GATE -->|pass| BUILD["hatchling build<br/>sdist + wheel"]
    BUILD --> DRY["TestPyPI dry-run"]
    DRY --> PYPI["PyPI"]
    CI["GitHub Actions<br/>(owns the pipeline)"] -.gates only.-> GATE
    TAG["git tags via hatch-vcs"] -.version.-> BUILD

Metadata lives once, in pyproject.toml; versions come from git tags

# pyproject.toml — the single source of metadata
[build-system]
requires   = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "hydrant"
requires-python = ">=3.9"
dynamic = ["version"]      # hatch-vcs from git tags

[tool.hatch.version]
source = "vcs"

artifact contract
  sdist: dist/hydrant-<ver>.tar.gz
  wheel: dist/hydrant-<ver>-py3-none-any.whl
  checksums published alongside, verified on install

The release command surface is the cross-component contract

hydrant release [--dry-run] [--publish]
  gates    lint + tests pass, tree clean, tag present
  build    sdist + wheel → dist/
  publish  PyPI upload — CI-only, gated on TestPyPI dry-run green
  tag      v<ver> created from the shipped commit

The switch replaces the build backend, not contributor workflows

Current
# setup.py — metadata + version in one file
setup(name="hydrant",
      version="0.9.0",
      packages=["hydrant"])

release: hand-run → upload from laptop
Target
# pyproject.toml — metadata; version from tags
[project]
name = "hydrant"
version = { source = "vcs" }

release: hydrant release → CI-gated publish
Program Design

The release wrapper is a short, sequential call tree

hydrant release --dry-run
  run_gates()            # pytest + ruff — must pass
  build_artifacts()      # hatchling build → dist/
  publish_dry_run()      # twine --repository testpypi

The file delta is small and mostly additive

 pyproject.toml                  # MODIFIED — hatchling backend, metadata
 + hydrant/release.py            # NEW — wrapper around CI-parity gates
 ~ .github/workflows/release.yml # MODIFIED — CI-gated build + publish
 + scripts/check_release.sh      # NEW — gates shared with CI
 - setup.py                      # REMOVED at slice 4

Seams: everything a release touches is fakeable or pointed at TestPyPI

hydrant release
  receives run_gates          -> fakeable: simulate failing lint in wrapper tests
  receives build_artifacts    -> fakeable: return stub paths
  receives publish            -> TestPyPI in CI; never PyPI from local

CI release job
  receives PYPI_TOKEN         -> CI secret, never in repo or local env
  receives version            -> from git tags via hatch-vcs

Session export on Settings

Small — no separate design records; design rides with the one Delivery Ticket
Problem to Solve

Users cannot download their own session data.

Success & measurement
  • A Settings button downloads all visible sessions as sessions.json.
  • 10k sessions export in < 2 s; the UI stays responsive.
System Design

A single read-only endpoint streams the caller's own sessions

sequenceDiagram
    participant U as Settings page
    participant C as API client
    participant R as GET /api/sessions/export
    participant S as sessionExport service
    participant D as DB
    U->>C: click Export
    C->>R: fetch export
    R->>S: buildExportRows(sessions)
    S->>D: query sessions (scoped to caller)
    D-->>S: rows
    S-->>R: JSON
    R-->>C: application/json
    C-->>U: blob → download sessions.json

The endpoint and row schema are the whole cross-component contract

GET /api/sessions/export
  auth: caller's session — own data only
  200  application/json
       { "sessions": SessionRow[] }

interface SessionRow {
  id: string;
  startedAt: string;         // ISO-8601
  endedAt: string | null;
  device: string;
  meta: Record<string, unknown>;
}
