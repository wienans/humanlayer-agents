design-discussion

Platform swap — design decisions

per create-design-discussion template · decisions made before product/technical design
Summary of change request

Replace the end-of-life STM32F103 with a new MCU, keeping every observable behavior identical so no customer re-qualifies their system.

Current State
  • Board ships on STM32F103 (Cortex-M3 @ 72 MHz); firmware built with IAR; single-bank flash boot.
  • Operators and SCADA rely on today's Modbus/HMI behavior; field test vectors exist but are re-run manually per site today.
Desired End State
  • New board on STM32H743 with identical behavior; customers cannot tell the boards apart.
  • Equivalence proven automatically on a HIL rig before factory cutover; no per-site re-qualification.
What we're not doing
  • No new features, no protocol changes, no HMI redesign, no feature refresh alongside the migration.
Proposed End-State Architecture

Before — today's board: one platform, one compiler, behavior tested per site:

flowchart TD
    APP["App layer\ncontrol · state · pid"] --> SRV["Service layer\ncomm · hmi · watchdog"]
    SRV --> HAL["HAL\nF1 driver impls"]
    HAL --> BSP["BSP F103\nIAR · single-bank boot"]
    BSP --> MCU["STM32F103\nCortex-M3 @ 72 MHz"]
    MCU --> HW["sensors · actuators · UARTs"]

After — app layers unchanged, platform layer rewritten below the HAL seam, equivalence gated by a HIL rig:

flowchart TD
    APP["App layer\ncontrol · state · pid\nUNCHANGED"] --> SRV["Service layer\ncomm · hmi · watchdog\nUNCHANGED"]
    SRV --> HAL["HAL\nH7 driver impls\nREWRITTEN"]
    HAL --> BSP["BSP H743\nGCC pinned · dual-bank boot\nNEW"]
    BSP --> MCU["STM32H743\nCortex-M7 @ 480 MHz"]
    MCU --> HW["same sensors · actuators · UARTs"]
    HIL["HIL rig — old board as oracle\nzero-tolerance equivalence"] -.gates cutover.-> MCU

Concise outline: freeze every wire contract; keep the app/service module graph as-is; rewrite HAL/BSP for H7; pin the GCC toolchain and reproduce builds; run every field vector on old vs new board with zero tolerance before cutover.

slices
  slice1  boot + clock + LED
  slice2  ADC/PWM control loop
  slice3  comms (Modbus/HMI)
  slice4  watchdog + safe-state
  slice5  full-system equivalence on HIL
gates
  entry  baseline suite green on old HW
  exit   full suite green on new HW + timing budgets met
Design Questions

open BSP: CubeMX-generated HAL or hand-written register-level?

CubeMX HAL (option A) gives vendor-supported, regenerable driver code — but injects vendor code into the build. Register-level (option B) is smaller and fully owned, but slower to write and more errata-sensitive.

Option A — HAL (recommended)
  bsp_adc_h7.c -> HAL_ADC_ConfigChannel(...)  // vendor regenerable
Option B — register-level
  bsp_adc_h7.c -> ADC1->IER = ...;            // full control, more risk

Recommendation: A — the HAL seam already isolates the app; vendor code stays quarantined in vendor/ with provenance tracked.

open Soft-float or hard-float for the new FPU?

The M7 has a hardware FPU; using it changes floating-point results in the last ULP, which can break byte-identical equivalence with the old M3.

Option A — soft-float (recommended)
  byte-identical math with F103 · simpler equivalence oracle
Option B — hard-float
  faster control math · must widen oracle tolerance to ±1 ULP

Recommendation: A — equivalence is the whole point of this migration; the control loop is not CPU-bound on the M7.

Resolved Design Questions

resolved Platform → STM32H743

Chosen for availability, 1 MB flash / 512 KB SRAM headroom, and dual-bank boot. Rejected: STM32F4 family (insufficient flash for future), STM32L4 (marginal performance), RISC-V parts (toolchain + vendor risk).

resolved Equivalence gate → zero-tolerance HIL oracle

The old board stays as a permanent oracle; every field vector runs on both boards and outputs must match exactly. Rejected: sampling a subset of vectors, or a manual site-by-site regression pass.

design:product

Reactor-control behavior contract

per create-prd template · synthesized from resolved decisions, no re-interview
Problem to Solve

The STM32F103 is end-of-life. The product must keep running with no change in what operators, the SCADA host, and commissioning engineers observe, because re-qualifying every deployed site is economically unacceptable.

What success looks like, and how we measure it
  • Behavioral equivalence — 100% of field functional test vectors pass on new hardware with identical pass criteria (the migration exit gate).
  • Real-time budgets — worst-case control-loop response and comm latency unchanged within measured budget.
  • Wire compatibility — Modbus frames and HMI protocol byte-identical.
  • No site re-qualification — single factory re-qualification before field cutover.
Proposed Solution
  • Keep the same product: same HMI, same SCADA contract, same control behavior.
  • Swap the platform under it — app code unchanged, BSP/HAL rewritten.
  • Prove equivalence on a hardware-in-the-loop rig where the old board is the oracle.
Alternative Solutions Considered
  • Feature refresh alongside the migration — rejected: triples re-qualification surface.
  • Per-site re-qualification — rejected: economically unacceptable.
Out of Scope
  • No new features, no protocol changes, no HMI redesign, no new diagnostics.
design:technical

H743 migration — Technical Design Document

per create-tdd template · System Design then Program Design · approval implicit by starting the next step
System Design

Cross-component architecture: how the pieces fit together, and how that arrangement changes from today. The delta is one coherent story — a platform swap, not a rewrite.

The app's component graph carries over unchanged; only the platform layer is rewritten

Application logic, services, and their dependency direction are today's design and stay today's design. What changes sits entirely below the HAL seam.

flowchart TD
    APP["App layer\ncontrol loops · state machine\nUNCHANGED"] --> SRV["Service layer\ncomm_modbus · hmi · watchdog\nUNCHANGED"]
    SRV --> HAL["HAL seam\ndriver interfaces\nREWRITTEN for H7"]
    HAL --> BSP["BSP\nclock · mem · pins\nNEW for H7"]
    BSP --> MCU["STM32H743"]
    MCU --> SENS["sensors · actuators · UARTs"]

Every wire interface stays byte-identical, so SCADA, HMI and sensors cannot tell the boards apart

The external contracts are frozen — they are the equivalence target. Represented as wire shapes, not prose:

Modbus RTU frame (unchanged)
  addr: u8 · function: u8 · data: n×u8 · crc16: u16
  functions: 03 read regs · 06 write reg · 16 write multi
  registers: 0x0000..0x01FF (inputs) · 0x1000..0x10FF (setpoints)

HMI packet (unchanged)
  { STX, cmd: u8, len: u8, payload[len], crc8 }

Sensor reads (unchanged)
  read_sensor(ch) -> u16   @ 1 kHz, SPI + GPIO chip-select

The delta is one platform swap — new MCU, remapped peripherals, new toolchain

Current — STM32F103
CPU        Cortex-M3 @ 72 MHz
Flash      64 KB (single-bank)
SRAM       20 KB
Clock      HSE 8 MHz → PLL
Periphs    F1 ADC/timer/UART map
Boot       single-bank flash
Toolchain  IAR EWARM
Packaging  compiler-version-dependent
Target — STM32H743
CPU        Cortex-M7 @ 480 MHz
Flash      1 MB (dual-bank)
SRAM       512 KB (plus cache)
Clock      HSE 8 MHz → PLL → 480 MHz
Periphs    H7 ADC/timer/UART map
Boot       dual-bank, vector relocation
Toolchain  GCC ARM (pinned, reproducible)
Packaging  build checksums in CI

Real-time and fault contracts are the equivalence oracle, not the goal

The only new software risk is silent behavioral divergence. The HIL rig makes divergence visible on every test vector — old board as oracle, new board as candidate, zero tolerance.

Register access stays inside BSP modules — the app never touches hardware

Pattern: every register and peripheral access lives in a bsp_* module; hal_* only calls BSP. File: bsp/bsp_adc.c, hal/hal_sensor.c.

Existing — bsp/bsp_adc.c (F1)
static ADC_TypeDef *const adc = ADC1;

void bsp_adc_init(void) {
  adc->CR2 |= ADC_CR2_ADON;      // F1-specific
}
uint16_t bsp_adc_read(adc_ch_t ch) {
  adc->SQR3 = ch & 0xF;          // F1 channel mux
  adc->CR2 |= ADC_CR2_SWSTART;
  while (!(adc->SR & ADC_SR_EOC)) {}
  return adc->DR;
}
Proposed — bsp/bsp_adc_h7.c (H7)
ADC_HandleTypeDef hadc1;         // H7 multi-core ADC

void bsp_adc_init(void) {
  hadc1.Instance = ADC1;
  HAL_ADC_ConfigChannel(&hadc1, &sConfig);
}
uint16_t bsp_adc_read(adc_ch_t ch) {
  HAL_ADC_Start(&hadc1);
  HAL_ADC_PollForConversion(&hadc1, HAL_MAX_DELAY);
  return (uint16_t)HAL_ADC_GetValue(&hadc1);
}

State machines are transition tables with a reducer, not if/else sprawl

Pattern: states and events declared once; one app_state_step reducer drives every transition. File: app/state/app_state.c.

Existing — app/state/app_state.c
static const trans_t TABLE[STATE_MAX][EVENT_MAX] = {
  [RUN][EV_FAULT]  = { .next = FAULT, .latch = true  },
  [FAULT][EV_ACK]  = { .next = SAFE,  .latch = false },
  [SAFE][EV_RUN]   = { .next = RUN,   .latch = false },
};

void app_state_step(StateCtx *ctx) {
  const trans_t *t = &TABLE[ctx->state][ctx->event];
  ctx->state = t->next;
  if (t->latch) ctx->fault = ctx->cause;
}
Proposed — same pattern, extended for cache/DMA
/* one new transition: DMA error must force SAFE immediately */
static const trans_t TABLE[STATE_MAX][EVENT_MAX] = {
  [RUN][EV_DMA_ERR]  = { .next = SAFE, .latch = true  },
};

void app_state_step(StateCtx *ctx) {
  const trans_t *t = &TABLE[ctx->state][ctx->event];
  ctx->state = t->next;
  if (t->latch) ctx->fault = ctx->cause;
  if (ctx->state == SAFE) bsp_mem_invalidate_dcache(rx_buf, RX_SZ);
}

DMA buffers are flushed before ownership handoff (new on H7)

Pattern: the D-cache makes CPU-written DMA buffers stale; flush before giving the buffer to a DMA-capable peripheral. File: hal/hal_comms.c. New pattern — no existing precedent on F1.

/* hal/hal_comms.c — before handing a TX buffer to the UART DMA */
bsp_mem_flush_dcache(tx_buf, TX_BUF_SIZE);
HAL_UART_Transmit_DMA(&huart2, tx_buf, TX_BUF_SIZE);

design-discussion

Release pipeline — design decisions

per create-design-discussion template · lighter than Large, same structure
Summary of change request

Make releases one-command and CI-gated instead of a manual laptop ritual.

Current State
  • Metadata + version live in setup.py; version bumped by hand.
  • Maintainers build and upload from their laptops; nothing is reproducible in CI.
Desired End State
  • hydrant release runs the same gates CI runs; publishing happens in CI only.
  • Version comes from git tags; artifacts verify by checksum.
What we're not doing
  • No dependency-manager migration, no build-tool change for the wider repo, no API changes.
Proposed End-State Architecture

Before — human on the critical path, two manual steps, version drifted:

flowchart LR
    DEV["Maintainer"] --> PYB["python -m build\n(laptop)"]
    PYB --> UPL["twine upload\n(manual)"]
    UPL --> PYPI["PyPI"]
    SET["setup.py\nversion 0.9.0\nhand-bumped"] -.drifts.-> PYB

After — one command; gates + publish owned by CI; version from tags:

flowchart LR
    DEV["Maintainer"] --> REL["hydrant release"]
    REL --> CI["GitHub Actions\nowner of gates + publish"]
    CI --> GATE{"gates\nlint + test + clean"}
    GATE -->|pass| BUILD["hatchling build"]
    BUILD --> DRY["TestPyPI dry-run"]
    DRY --> PYPI["PyPI"]
    TAG["git tags\nhatch-vcs"] -.version.-> BUILD

Concise outline: one entrypoint, shared gates, staged publish. A thin hydrant.release wrapper mirrors exactly what CI runs, so the local dry-run is a true rehearsal.

Design Questions

open Build backend: hatchling, poetry, or pdm?

Option A — hatchling (recommended)
  single-purpose backend · stdlib-adjacent · minimal surface
Option B — poetry
  backend + dependency resolution + lockfile in one
Option C — pdm
  modern + PEP 621, heavier new workflow for contributors

Recommendation: A — this effort only changes packaging + publishing; a full project manager (B/C) drags in dependency-resolution changes that are out of scope.

open Version source: hatch-vcs or manual bump?

Option A — hatch-vcs (recommended)
  version = latest git tag · impossible to drift
Option B — manual version field
  familiar, but a release can ship the wrong number

Recommendation: A — one source of truth; tagging becomes the release act.

Resolved Design Questions

resolved CI is the only publisher

Local hydrant release never touches PyPI; publishing requires the CI token. Rejected: local publish with token on disk (secret sprawl) and fully-manual publish (the status quo this effort exists to kill).

resolved TestPyPI dry-run is a hard gate before live publish

Every release uploads to TestPyPI first and installs in a fresh venv before PyPI. Rejected: publish directly to PyPI (rollback pain on a bad artifact).

CLI commands hang off the argparse entrypoint

Pattern: subcommands registered on one argparse parser in the CLI module; no logic in the entrypoint. File: hydrant/cli.py.

Existing — hydrant/cli.py
def main(argv=None) -> int:
    parser = argparse.ArgumentParser(prog="hydrant")
    parser.add_argument("--verbose", action="store_true")
    args = parser.parse_args(argv)
    return run(args)
Proposed — new subcommand, same pattern
def main(argv=None) -> int:
    parser = argparse.ArgumentParser(prog="hydrant")
    parser.add_argument("--verbose", action="store_true")
    sub = parser.add_subparsers(dest="command")
    rel = sub.add_parser("release")
    rel.add_argument("--dry-run", action="store_true")
    rel.add_argument("--publish", action="store_true")
    return dispatch(args)      # release() lives in hydrant.release

open Export as one JSON blob, or stream rows?

Option A (recommended): one application/json blob — matches the 10k-row budget, simplest to test and serve.
Option B: NDJSON stream — scales to millions of rows, adds streaming plumbing this change doesn't need.

resolved Export is scoped to the caller

The endpoint returns the authenticated user's sessions only; no admin/global export. Rejected: any shared or cross-user export.

Concise System Design

A single read-only endpoint streams the caller's own sessions

Patterns to Follow

Existing codebase patterns the implementation must follow, with file locations and snippets.

API calls go through the single fetch wrapper

Pattern: every endpoint call lives in src/lib/api-client.ts; components never call fetch directly. File: src/lib/api-client.ts.

Existing — src/lib/api-client.ts
async function get<T>(path: string): Promise<T> {
  const res = await fetch(path, { credentials: "include" });
  if (!res.ok) throw new ApiError(res.status);
  return res.json();
}

export function getSessions(): Promise<Session[]> {
  return get<Session[]>("/api/sessions");
}
Proposed — same wrapper, blob variant
export async function getSessionsExport(): Promise<Blob> {
  const res = await fetch("/api/sessions/export", { credentials: "include" });
  if (!res.ok) throw new ApiError(res.status);
  return res.blob();
}

Page components stay thin over a hook

Pattern: page logic lives in a use* hook; the component renders state and wires events. File: src/routes/settings.tsx.

Existing — src/routes/settings.tsx
export function SettingsPage() {
  const { sessions } = useSessions();
  return <SessionList sessions={sessions} />;
}
Proposed — export wired through a hook
export function SettingsPage() {
  const { sessions } = useSessions();
  const { run, status } = useSessionExport();
  return (
    <>
      <SessionList sessions={sessions} />
      <ExportButton onExport={run} disabled={status === "loading"} />
    </>
  );
}
